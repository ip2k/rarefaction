# Embedded C, JieLi and WebAssembly

Rarefaction is an MCP client-facing server that composes LSP queries. Register
it with Codex as an **MCP**, not as an editor language server. Its `c` profile
starts clangd; `rust` starts rust-analyzer; `wasm` starts wat_server.

## C/C++ and firmware

Use a compilation database generated by the actual build, with include paths,
preprocessor defines and language flags for each translation unit. CMake can
export one with `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`; other build systems need
their own command export/capture. A local `compile_flags.txt` is useful for a
small project, but does not enumerate translation units for background indexing.
No compiler is executed by the database-preparation tool.

A database captured in a LAN container needs its source, SDK and sysroot paths
mapped to matching local files. Remapping a path does not fetch the headers.
Keep vendor material in its existing private/ignored location. Example:

```bash
python3 tools/prepare_clangd.py remote/compile_commands.json \
  /path/to/project/.clangd-analysis/compile_commands.json \
  --map /workspace/project=/path/to/project \
  --map /opt/sdk=/path/to/local/sdk
```

Set `profiles.c.args` in that project's `.rarefaction.json`:

```json
{
  "profiles": {
    "c": {
      "args": ["--background-index", "--log=error", "-j=2",
               "--compile-commands-dir=/path/to/project/.clangd-analysis"]
    }
  }
}
```

Restart the MCP after changing settings. Open source files synchronize after
saved edits; changing a compile database requires the build export to stay
current. Background indexing can lag or stop before completion. A ready server
means its prerequisites are detected, not that all build variants or callers
have been proven complete. Missing flags and unindexed files reduce recall.

## M-VAVE FM1 / JieLi

The local Lunar Modulator project's hardware documentation identifies its FM1
as **AC791N/WL82, pi32v2**, rather than AC97. Its compile-check script uses
JieLi's compiler with `-target pi32v2 -mcpu=r3`. That backend is not part of
upstream clangd; installing clangd does not add a JieLi compiler or Rust target.
The portable C/C++ engine code can still be analyzed using its desktop build
configuration. Firmware-specific code needs a separate analysis configuration.

The preparation tool accepts both `arguments` arrays and simple POSIX `command`
strings. It rejects compound shell commands and compiler wrappers, preserves
include paths/defines, remaps container paths, and refuses to overwrite the
input. With `--jieli`, it strips target, CPU, LLVM backend and target-feature
flags and requires an explicit replacement **analysis** target:

```bash
python3 tools/prepare_clangd.py remote/compile_commands.json \
  /path/to/project/.clangd-analysis/compile_commands.json \
  --map /workspace/project=/path/to/project \
  --jieli --analysis-target i386-unknown-none-elf
```

This example is an approximation with 32-bit pointers, **not a pi32v2 ABI
model**. Host libc headers may also be unsuitable for it. Use the real local
SDK include paths and an explicitly reviewed analysis shim if vendor-specific
builtins/assembly cannot parse. Do not replace firmware headers or flags with
analysis shims, do not infer register layouts from the substitute target, and
do not use clangd diagnostics as evidence that firmware builds or runs.
Only the actual JieLi compiler validates backend-specific source. No tool here
flashes or communicates with a device.

The FM1 sequencer smoke check uses eight existing portable C translation units
and flags from `engines/mk/seq.mk`, in an external cache database. That confirms
source orientation for that slice, not complete SDK or whole-firmware indexing.
The firmware workspace and its pending edits are left unchanged.

## Rust embedded and Wasm

Use `profiles.rust.initializationOptions` to pass rust-analyzer target/features:

```json
{
  "profiles": {
    "rust": {
      "initializationOptions": {
        "cargo": { "target": "wasm32-unknown-unknown", "features": ["web"] }
      }
    }
  }
}
```

Use a target your Rust toolchain actually supplies (`rustup target list
--installed`). Rust/C-to-Wasm support here means source-language analysis with
the correct target configuration, not compilation or execution of Wasm. Standard
Rust does not supply a pi32v2 target. Analyze portable Rust components on a
supported target; a JieLi firmware integration still needs an actual compiler,
ABI and FFI implementation. Macro expansion/generated-code coverage may need
explicitly enabled build scripts and proc macros (disabled by default).

For Emscripten C/C++, export its real compile commands and remap its sysroot
and project paths. Do not strip the supported wasm32 target. Flags and sysroot
availability remain the build system's responsibility.

## WAT and binary Wasm

Install `wat_server` from [WebAssembly Language Tools releases](https://github.com/g-plane/wasm-language-tools/releases).
The verified macOS installation uses the arm64 v0.11.0 binary. Its `.wat`
functions support call hierarchy and source excerpts. `.wast` scripts are
outside this profile's supported formats. To inspect a `.wasm` binary, create
a `.wat` representation using a disassembler such as wasm-tools or WABT and
orient on that text. Stripped binaries may lack meaningful symbol names;
source/debug mappings and JavaScript/Rust/C interop are separate evidence.

Sources: [clangd compile commands](https://clangd.llvm.org/design/compile-commands),
[rust-analyzer configuration](https://rust-analyzer.github.io/book/configuration),
[WebAssembly Language Tools](https://github.com/g-plane/wasm-language-tools).
